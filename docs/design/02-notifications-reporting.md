# 02. 通知・レポーティング設計書

SUP体験事業 予約管理システム / 担当領域：通知（LINE）とレポーティング（週次/日次/月次・各種ログ）

- 対象システム：Google Apps Script（GAS）
- 関連ファイル
  - `sup_reservation.gs` … 予約メール処理・カレンダー登録・在庫連動（`notifySlotReduction_`）・LINE通知（`postToLine` / `sendLineNotification` / `buildLineMessage`）
  - `sup_analytics.gs` … 売上集計・週次レポート（Claude API `claude-opus-4-8` + Google Docs）・LINE通知（`sendLineMessage_`）
- 通知チャネル：LINE Messaging API（push）。スクリプトプロパティ `LINE_CHANNEL_TOKEN` / `LINE_USER_ID`
- 想定読者：実装者・運用管理者（support@peg-retreat.com）

> 本書は現行コードの実装を起点に「実装するとどうなるか」まで踏み込んだ設計である。現状実装と差分がある箇所は「現状」「拡張」を明記する。

## 0. 現状実装サマリー（把握した事実）

通知・レポーティングに関係する現行の挙動を、推測を排して整理する。

### 0.1 予約側（`sup_reservation.gs`）

- `importEmails_` が30分ごと（`importReservationEmails` トリガー）にGmailを検索し、予約タイプを `detectBookingType`（確定/仮予約/変更/キャンセル/不明）に分類。
- 新規行は `appendToSheet`、既存行（予約番号一致）は `updateRow`、キャンセルは `handleCancellation` で処理。
- 通知種別の決定は `resolveLineNotifyType(bookingType, r, instructorNeeded)`：
  - キャンセル → `'キャンセル'`
  - 変更 → `'変更'`
  - 仮予約 → `'仮予約'`
  - 日付/時間/人数のいずれか欠落 → `'要確認（情報不足）'`
  - 確定 かつ 追加インストラクター必要（6名以上, `INSTRUCTOR_THRESHOLD = 6`）→ `'要対応（追加インストラクター必要）'`
  - 確定（通常）→ `'確認通知'`
  - 上記以外 → `null`（通知しない）
- `sendLineNotification` が **同一種別の重複送信を W列「LINE通知済み」で抑止**（カンマ区切りで種別を記録）。`forceResend=true`（キャンセル）は既通知でも送信。
- `buildLineMessage` のメッセージは `確認通知` 以外をすべて「⚠️ 要対応通知」ヘッダーにする。日付/時間帯（午前午後）/人数/犬有無/予約サイト/枠状況（合計・上限・残数）を含む。
- `notifySlotReduction_` は新規の確定/仮予約で **GitHub Actions（`repository_dispatch` `reduce_slot`）** を叩いて他OTA在庫を減算する。`SLOT_SYNC_ENABLED='true'` のときのみ実行（既定OFF）。**結果は `Logger.log` に記録するのみで、LINE通知・成否ログ記録は一切ない（＝今回の主要な拡張対象）**。
- `registerApprovedToCalendar` は1時間ごと。カレンダー登録の成否は `Logger.log` のみ。**LINE通知なし**。
- `checkCapacityWarnings` は容量警告を **`Logger.log` に出すだけでLINE送信していない（拡張対象）**。

### 0.2 分析側（`sup_analytics.gs`）

- `generateWeeklyReport`（毎週月曜8:00トリガー `setupWeeklyReportTrigger`）が
  1. `buildWeeklySnapshot` で先週/前週/月累計/年累計/前年同期/先行予約/着地見込み/アラートを集計
  2. `callClaudeAPI`（`claude-opus-4-8`, max_tokens 1800, 429/529で最大4回リトライ）で分析生成
  3. `createWeeklyReportDoc` でGoogle Docs作成（リンクを知っている全員が閲覧可）
  4. `writeWeeklyReport` で【週次レポート】シートに追記
  5. `sendLineMessage_` でサマリー＋Docリンクを通知
- `buildWeeklySnapshot` 内に `alerts[]` 自動検知ロジックあり（年累計<80%、月<80%、前週比-20%超、先週0件）。**現状このアラートはDocに載るのみで、単独のLINEアラートにはなっていない（拡張余地）**。
- 日次/月次/年間ダッシュボードはシート更新のみ。**LINE/Docレポート配信はない（拡張対象）**。

### 0.3 通知の信頼性に関する現状の弱点

| 項目 | 現状 | 課題 |
|---|---|---|
| 送信リトライ | `postToLine`/`sendLineMessage_` ともに **リトライなし**（try/catchでログのみ or muteHttpExceptions） | 一時的失敗で通知ロスト |
| 二重送信防止 | 予約通知は W列で種別単位に抑止。週次・在庫連動は **抑止なし** | トリガー二重起動で重複 |
| 通知ログ | **専用ログなし**（`Logger.log` は永続性が低い） | 監査・再送・障害解析ができない |
| 失敗の可視化 | LINE送信失敗・在庫連動失敗・カレンダー失敗は管理者に届かない | 障害が放置される |

## 1. 通知イベント設計

### 1.1 通知マトリクス（誰に・いつ・何を）

宛先は当面すべて **運用管理者（`LINE_USER_ID` の1名）**。将来の宛先分離（オペレーター/経営者）に備え、重要度（severity）と種別（type）でフィルタできる設計にする。

| # | イベント | 種別(type) | 重要度 | 通知タイミング | まとめ | 現状/拡張 |
|---|---|---|---|---|---|---|
| 1 | 新規確定予約（通常） | `予約.確定` | INFO | 取込時・即時 | 〇（バッチ集約可） | 現状あり（`確認通知`） |
| 2 | 新規確定予約（6名以上=要追加IS） | `予約.要対応IS` | WARN | 即時 | × 個別 | 現状あり |
| 3 | 仮予約（リクエスト） | `予約.仮予約` | ACTION | 即時 | × 個別 | 現状あり |
| 4 | 情報不足で要確認 | `予約.要確認` | WARN | 即時 | × 個別 | 現状あり |
| 5 | 予約変更 | `予約.変更` | WARN | 即時 | × 個別（前後明示） | 現状あり（**前後差分は拡張**） |
| 6 | キャンセル | `予約.キャンセル` | INFO | 即時（強制再送） | 〇 | 現状あり |
| 7 | 容量上限到達/超過 | `枠.容量警告` | WARN | 取込後バッチ | 〇（日×午前午後でまとめ） | **拡張**（現状ログのみ） |
| 8 | 在庫連動 成功 | `在庫.成功` | INFO | 実行時 | 〇（日次サマリーに集約推奨） | **拡張** |
| 9 | 在庫連動 失敗/未送信 | `在庫.失敗` | ALERT | 即時 | × 個別 | **拡張** |
| 10 | カレンダー登録 失敗 | `システム.カレンダー失敗` | ALERT | 実行時 | 〇（1実行分まとめ） | **拡張** |
| 11 | LINE送信失敗（自己診断） | `システム.通知失敗` | ALERT | 次回実行時に検知通知 | 〇 | **拡張** |
| 12 | スクリプト実行エラー（例外） | `システム.エラー` | ALERT | 発生時 | × | **拡張** |
| 13 | 週次レポート | `レポート.週次` | INFO | 毎週月8:00 | ‐ | 現状あり |
| 14 | 日次サマリー | `レポート.日次` | INFO | 毎朝7:00 | ‐ | **拡張** |
| 15 | 月次サマリー | `レポート.月次` | INFO | 月初9:00 | ‐ | **拡張** |
| 16 | 経営アラート（達成率/前週比） | `レポート.アラート` | WARN | 週次内 or 検知時 | 〇 | **拡張**（snapshot.alertsを単独化） |

重要度の定義：

- **INFO**：把握用。読まなくても業務が止まらない。まとめ通知の対象。
- **WARN**：確認推奨。当日中に目を通す。
- **ACTION**：人間の操作が必要（仮予約承認など）。
- **ALERT**：要即時対応。在庫不整合・システム障害など放置すると損失/オーバーブッキング。

### 1.2 通知過多を避ける設計

通知が多すぎると重要なALERTが埋もれる。以下の3層で抑制する。

1. **重要度フィルタ（しきい値）**
   - スクリプトプロパティ `NOTIFY_MIN_SEVERITY`（既定 `INFO`）で、これ未満は送らない。
   - 繁忙期は `WARN` に上げてINFOを止め、レポートに集約。
2. **まとめ通知（バッチ集約）**
   - 1回の `importEmails_` 実行内で発生した複数の `予約.確定`（INFO）は **1通に集約**して送る（新規N件サマリー）。要対応系（ACTION/ALERT）は従来どおり個別即時。
   - 容量警告は「日付×午前/午後」で1通にまとめる（`checkCapacityWarnings` の `warnings[]` をそのまま整形）。
   - 在庫連動の成功（INFO）は即時送信せず **日次サマリーに集約**。失敗のみ即時ALERT。
3. **重複/連投抑止**
   - 既存の W列方式（種別単位）を踏襲。
   - 同一内容の連投は後述の通知ログ + ハッシュで二重送信防止。
   - 容量警告は「同一スロットを当日すでに警告済みなら再送しない」フラグをログ側に持つ。

### 1.3 集約のための新ヘルパー（設計）

```text
NotificationBus（擬似モジュール）
  push(event)        // {type, severity, title, body, dedupeKey, slotKey?}
  flushBatch()       // importEmails_ / register... の末尾で呼ぶ
                     // INFO同type → 1通に結合、ACTION/ALERTは即時に送信済み
sendNotification(event)
  1. severity < NOTIFY_MIN_SEVERITY ならスキップ（ログには残す）
  2. dedupeKey が通知ログに既存ならスキップ
  3. postToLine_(text) を最大3回リトライ
  4. 結果を通知ログシートに記録（成功/失敗/リトライ回数）
```

## 2. LINE通知メッセージ仕様

LINEはテキストpush（`messages:[{type:'text'}]`）。1メッセージ上限5000文字に収まる範囲。各テンプレは現行 `buildLineMessage` のスタイル（区切り線・絵文字ラベル）を踏襲する。

共通ヘッダールール：

- INFO：`【お知らせ】`
- WARN：`【要確認】`
- ACTION：`【要対応】`
- ALERT：`🚨【至急】`

### 2.1 新規確定予約（INFO・集約）

単発：
```
【お知らせ】SUP予約が入りました
─────────────────
📅 日付：2026/7/15
🕐 時間帯：午前（9:30）
👥 人数：4名（大人×3・小人×1）
🐕 犬：なし
🏪 予約サイト：じゃらんnet
📊 枠状況（午前）合計：6名 / 上限8名（残2名）
```
集約（同一実行で複数件）：
```
【お知らせ】新規予約 3件
─────────────────
1) 7/15(午前) じゃらん 4名 残2名
2) 7/16(午後) アソビュー 2名 残6名
3) 7/20(午前) AJ 3名 残5名
※詳細はスプレッドシート参照
```

### 2.2 要対応：追加インストラクター必要（WARN）

```
【要対応】追加インストラクターが必要な予約
─────────────────
⚠️ 対応理由：6名以上のため追加IS手配が必要
📅 7/22(午前 9:30) ／ 👥 7名
🏪 アソビュー ／ 🐕 なし
👨‍🏫 追加インストラクター担当：未定
👉 スプレッドシートR列に担当を記入してください
```

### 2.3 仮予約／リクエスト（ACTION）

```
【要対応】仮予約（リクエスト）が入りました
─────────────────
📅 7/18(午後 13:30) ／ 👥 5名 ／ 🏪 じゃらん
📊 枠状況（午後）合計：7名 / 上限8名（残1名）
👉 受入可否を判断し、OTA管理画面で承認/却下してください
```

### 2.4 予約変更（WARN・前後明示）

現行 `buildLineMessage` は変更後のみ表示。**変更前後の差分を明示するよう拡張**する。変更前は更新前のシート行（`updateRow` 内で `setValue` する前に旧値を退避）を使う。

```
【要確認】予約内容が変更されました
─────────────────
🏪 じゃらん ／ 予約番号 ABC123 ／ 山田様
変更項目：
  日付　 7/15 → 7/22
  時間帯 午前 → 午後
  人数　 4名 → 6名 ⚠️追加IS必要に
📊 変更後の枠状況（7/22 午後）合計：6名 / 上限8名（残2名）
👉 カレンダーは手動更新が必要です（自動反映は無効）
```
> 注：現行 `onEdit` はカレンダー自動反映を意図的に無効化済み。変更通知に「手動更新」を明記すること。

### 2.5 キャンセル（INFO・強制再送）

```
【お知らせ】予約がキャンセルされました

🏪 アソビュー ／ 7/16(午後) ／ 👥 2名 ／ 山田様
📊 解放後の枠状況（午後）合計：5名 / 上限8名（残3名）
```

```
👉 各OTA管理画面で在庫を手動で-4してください

```

```
対象：7/15 午前 -4名

```

## 3. 通知の信頼性

### 3.1 送信リトライ

`postToLine` / `sendLineMessage_` を共通の `postToLine_(text)` に統合し、リトライを実装する（Claude APIの `callClaudeAPI` と同じ方針）。

```text
postToLine_(text):
  token/userId 未設定 → 通知ログに「設定不備」を記録して return
  retryDelays = [1000, 3000, 9000]    // 指数的バックオフ
  retryable   = [429, 500, 502, 503]  // LINE一時障害
  for attempt in 0..3:
    res = UrlFetchApp.fetch(push, {muteHttpExceptions:true})
    code = res.getResponseCode()
    if code == 200: return {ok:true, attempts:attempt+1}
    if code in retryable and attempt<3: sleep(retryDelays[attempt]); continue
    break                              // 400/401/403は再試行しても無駄
  return {ok:false, code, body}        // 呼び出し側で失敗ログ + フォールバック
```

- GAS実行は最大6分。リトライ合計は十数秒に抑える（上記で最大13秒）。
- `400/401/403`（トークン無効・宛先不正）は即時失敗扱い。次回実行時に「通知失敗が継続」をALERT化。

### 3.2 二重送信防止

- **予約通知**：現行の W列「LINE通知済み」（種別カンマ区切り）を継続。
- **横断的な dedupeKey**：通知ログに `dedupeKey` を持ち、送信前に存在チェック。
  - 予約系：`{予約番号}_{種別}_{変更後ハッシュ}`
  - 容量警告：`cap_{YYYY-MM-DD}_{AM|PM}_{date}`（日付＝当日。同日同スロットの再警告抑止）
  - 在庫連動：`slot_{date}_{time}_{予約番号}`
  - 週次/日次/月次：`weekly_{対象週}` / `daily_{YYYY-MM-DD}` / `monthly_{YYYY-MM}`（トリガー二重起動対策）
- 週次・日次・月次は「同キーが当日すでに成功記録あり」ならスキップ。

### 3.3 通知ログ（スプレッドシート）

分析用スプレッドシート（または予約用）に **`【通知ログ】`** シートを新設。

| 列 | 項目 | 例 |
|---|---|---|
| A | 送信日時 | 2026/6/30 09:05:12 |
| B | 種別(type) | 在庫.失敗 |
| C | 重要度 | ALERT |
| D | dedupeKey | slot_2026-07-15_09:30_ABC123 |
| E | 宛先 | LINE_USER_ID |
| F | 件名/要約 | OTA在庫連動失敗 7/15午前 |
| G | 本文（全文 or 先頭200字） | 🚨【至急】… |
| H | 結果 | 成功 / 失敗 / スキップ(dedupe) / スキップ(severity) / 設定不備 |
| I | HTTPコード | 200 / 422 |
| J | リトライ回数 | 1 |
| K | 関連キー | 予約番号 ABC123 / 行12 |

運用：

- 行数肥大対策として、`trimNotificationLog_`（月次トリガー）で **古い行（例：180日超）を削除/アーカイブ**。
- 「直近の `失敗` を集計し、未解消が続けば再ALERT」する自己診断 `selfCheckNotifications_` を日次サマリー処理に同梱。
- ログ書き込み自体が失敗してもメイン処理は止めない（try/catchで握る）。

## 4. レポーティング設計

### 4.1 レポート一覧と配信

| レポート | 内容 | 生成 | 配信 | トリガー（時間主導） | データ源 |
|---|---|---|---|---|---|
| 週次レポート（現行） | 先週実績・着地見込み・前年比・Claude分析 | Google Docs + シート | LINEサマリー+Docリンク | 毎週月 8:00（`generateWeeklyReport`） | 統合DB / 【目標】 |
| 日次サマリー（拡張） | 当日参加・前日新規・翌日予定・要対応 | LINEテキスト | LINE | 毎朝 7:00 | 予約一覧 + 統合DB |
| 月次サマリー（拡張） | 前月確定・目標比・前年比・チャネル | LINE + 月次ダッシュボード | LINE | 毎月1日 9:00 | 統合DB / 【目標】 |
| 在庫連動 実行ログレポート（拡張） | 当日の在庫連動 成功/失敗一覧 | LINE（失敗時のみ詳細）+ 通知ログ集計 | LINE | 毎日 20:00 | 通知ログ（在庫.*） |
| エラーレポート（拡張） | 当日のALERT/失敗の集計 | LINE | LINE | 日次サマリーに同梱 or 18:00 | 通知ログ（失敗行） |

### 4.2 日次サマリー設計（`generateDailySummary`）

- 統合DB/予約一覧から **当日参加分**を抽出（午前/午後・人数・犬・6名以上ハイライト）。
- 前日24hの新規予約件数・金額（予約一覧の処理日時 or 統合DB取込日時）。
- 翌日参加予定。
- 追加IS担当が「未定」のまま当日を迎える予約があれば WARN を付す。
- 当日参加0件なら通知を送らない or 「本日参加なし」1行（`NOTIFY_MIN_SEVERITY` 次第）。
- トリガー：`ScriptApp.newTrigger('generateDailySummary').timeBased().everyDays(1).atHour(7)`。

### 4.3 月次サマリー設計（`generateMonthlySummary`）

- 月初に **前月**を対象に集計（`updateMonthlyDashboard` の集計結果を流用）。
- 目標比・前年同月比・チャネル構成比を LINE 1通に。
- トリガー：`onMonthDay(1).atHour(9)`（GASは `everyDays` + 日付判定でも可）。

### 4.4 在庫連動 実行ログレポート設計

現状 `notifySlotReduction_` はログのみ。以下を実装：

1. 実行ごとに通知ログへ `在庫.成功`/`在庫.失敗` を記録（HTTPコード・dry_run有無・対象スロット・発生元サイト・予約番号）。
2. **失敗は即時 ALERT（2.7）**。
3. 1日分を 20:00 に集計し、`成功N件 / 失敗M件`、失敗があれば対象一覧を LINE 通知（`reportSlotSyncDaily`）。
4. `SLOT_SYNC_DRY_RUN='true'` の間は「dry_runのため実在庫は変更していない」旨を明記（誤認防止）。

### 4.5 エラーレポート設計

- メインバッチ（`importEmails_` / `registerApprovedToCalendar` / `normalizeAllCSV` / `generateWeeklyReport`）を `try/catch` でラップし、捕捉した例外を `reportError_(fnName, error)` で通知ログ + ALERT。
- カレンダー登録失敗（現行はループ内 `Logger.log` のみ）は **件数を集計して1実行1通**にまとめてALERT。
- 日次で通知ログの `失敗` 行を集計し、未解消が続くものを再掲（サイレント障害の防止）。

### 4.6 トリガー一覧（設計後の想定）

| 関数 | 種別 | 頻度 |
|---|---|---|
| `importReservationEmails` | 時間主導 | 30分ごと（現行） |
| `registerApprovedToCalendar` | 時間主導 | 1時間ごと（現行） |
| `generateWeeklyReport` | 週次 | 月 8:00（現行） |
| `generateDailySummary` | 日次 | 毎日 7:00（新規） |
| `reportSlotSyncDaily` | 日次 | 毎日 20:00（新規） |
| `generateMonthlySummary` | 月次 | 1日 9:00（新規） |
| `trimNotificationLog_` | 月次 | 1日 3:00（新規） |

> `setupTriggers` / `setupWeeklyReportTrigger` に追記して一元管理する。トリガー二重登録を避けるため、登録前に同名トリガーを削除する現行パターンを踏襲。

## 5. 管理者の運用フロー

要対応通知（ACTION/ALERT）を受けたとき人間がどう動くか。LINE本文末尾の「👉」行に常に次アクションを書く。

### 5.1 仮予約（リクエスト）承認フロー

1. ACTION通知（2.3）受信。
2. スプレッドシートで枠状況・追加IS要否を確認。
3. OTA管理画面で **承認 or 却下**。
4. 承認なら確定メールが届き、次回 `importEmails_` で `updateRow` → ステータスが `承認済` に。
5. `registerApprovedToCalendar` が自動でカレンダー登録（最大1時間）。急ぐ場合は手動実行。
6. 却下時はシートのステータスを `却下` に変更（容量集計から除外される）。

### 5.2 追加インストラクター手配（6名以上）

1. WARN通知（2.2）受信。
2. 担当ISに連絡し、確定したらシート **R列「追加インストラクター担当」** に氏名を記入。
3. 記入後にカレンダー登録すると、タイトルに `【要追加インストラクター】`、説明に担当名が反映（`buildCalendarEvent`）。
4. 当日まで「未定」が残る予約は日次サマリーで再掲される（4.2）。

### 5.3 容量警告・在庫手動調整

1. WARN（2.6 満員/超過）または ALERT（2.7 在庫連動失敗）受信。
2. 満員/超過 → 各OTA管理画面で当該スロットを **受付停止**。
3. 在庫連動失敗 → 本文の「対象スロット・減算数」に従い、各OTAで在庫を手動減算。
4. 超過（オーバーブッキング発生済み）→ 顧客へ時間帯変更を打診、またはIS増員で対応可否を判断。
5. 対応後、通知ログ該当行のK列等にメモ（任意）。再発する場合は `SLOT_SYNC_ENABLED` / `GITHUB_TOKEN` 設定を点検。

### 5.4 変更予約への対応

1. WARN通知（2.4・前後差分）受信。
2. 日付/時間帯が変わった場合 **カレンダーを手動で修正**（自動反映は無効）。
3. 人数が6名以上に増えた場合は 5.2（追加IS手配）へ。
4. 枠超過に転じた場合は 5.3 へ。

### 5.5 システムエラー・通知失敗

1. ALERT（2.8）受信。
2. 【通知ログ】シートで失敗行・HTTPコードを確認。
3. `401/403` → LINEトークン（`LINE_CHANNEL_TOKEN`）の失効を疑い再発行。
4. カレンダー失敗 → 日時フォーマット（H列/I列）を確認し手動修正後に `registerApprovedToCalendar` を再実行。
5. Claude API失敗（週次）→ 一時障害ならトリガー次回で自動回復。継続するなら `ANTHROPIC_API_KEY` を確認。
