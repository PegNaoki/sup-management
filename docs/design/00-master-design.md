## 1. 何を作るか（目的）

複数のOTA（じゃらん遊び体験 / アクティビティジャパン / アソビュー / ウラカタ）と直接予約を、
**1つのスプレッドシートを「真実の記録」として一元管理**し、以下を自動化する。

1. **予約取込**: 各OTAの予約メールを自動でスプレッドシート・Googleカレンダーに反映
2. **在庫連動**: あるOTAで予約が入ったら、同じ枠を売る他OTAの在庫を自動で減らす（ダブルブッキング防止）
3. **通知**: 予約・変更・キャンセル・要対応・障害をLINEで適時通知
4. **分析**: 売上実績を目標と突合し、週次でClaude AIが分析レポートを自動生成

## 2. 全体像（3層アーキテクチャ）

```
┌─ Google基盤（ハブ / System of Record）──────────────┐
│  Gmail → Apps Script → スプレッドシート（真実の記録）  │
│                ├→ Googleカレンダー                      │
│                ├→ LINE（通知）                          │
│                └→ Claude API（週次分析）                │
└──────────────────┬──────────────────────────────────┘
                   │ repository_dispatch / cron
┌─ GitHub Actions（ブラウザ実行基盤）─────────────────┐
│  Playwright + Chromium → 各OTA管理画面を操作          │
│    ・在庫減算（書込）  ・予約/在庫の読取（リコンサイル）│
└──────────────────┬──────────────────────────────────┘
                   │ ブラウザ自動操作
        各OTA（じゃらん / アソビュー / AJ / ウラカタ）
```

**なぜこの構成か**: GASはGoogleサービスと無料・無管理で連携できるが**ブラウザを動かせない**。OTAはAPIがなくUI操作が必須のため、ブラウザを動かせるGitHub Actionsに委譲する。詳細は [03章 §1](./03-architecture-ops.md)。

## 4. 横断的な設計判断（3編で共通の前提）

これらは3つの詳細設計をまたぐ重要な決定事項。

1. **スプレッドシートが唯一の真実の記録（System of Record）**。OTAやカレンダーはその写像。
2. **在庫操作は「売り元以外」を対象**にする。予約が入ったサイト自身は既に減っているため触らない。
3. **安全側のデフォルト**: 在庫を実際に動かす操作は `SLOT_SYNC_ENABLED` + `DRY_RUN=false` の二重ゲート。
4. **失敗は握りつぶさない**: 在庫操作・通知・カレンダーの失敗は必ずLINE ALERTで人へ。サイレント失敗を排除。
5. **べき等性は必須**: 同じメール・同じ差分・同じdispatchを2回処理しても二重作用しない（`byMsgId`、`SLOT_SYNCED`、`dedup_key`）。
6. **段階導入**: じゃらん本番化 → 監視 → マルチOTA → リコンサイルの順。前段の完了条件を満たすまで次に進まない。

## 5. 在庫連動の核心フロー（3編を貫く要約）

```
[予約発生] 他OTAで予約 → メール → GAS取込 → スプレッドシート更新
                                          │
         ┌────────────────────────────────┘
         │ 確定 かつ 売り元以外に在庫連動対象あり
         ▼
[減算] notifySlotReduction_ → dedup_key照合（二重防止）
       → repository_dispatch(reduce_slot, slot_delta=-N, dedup_key)
       → Actions → Playwright → 対象OTAの枠を -N（前後残数を検証）
         │
         ├ 成功 → SLOT_SYNCED記録 + 通知ログ（INFO/日次集約）
         └ 失敗 → LINE ALERT（オーバーブッキング懸念・手動対応依頼）

[キャンセル] → handleCancellation → カレンダー削除 → restoreSlotInventory_（+N 戻し）
[変更]      → 差分判定（classifyChange_）→ 旧枠+戻し / 新枠-減算
```

- 戻し（plus）操作は現スクリプト未対応 → `slot_delta`（符号付き）対応が必要（[01章 §3.4](./01-reservation-lifecycle.md)）。
- dispatch成功(204)は「実在庫が減った」ことを**保証しない**。実結果の検証/通知は [02章 §2.7](./02-notifications-reporting.md)・[03章 §4.4](./03-architecture-ops.md)。

## 6. 推奨MVP（次にやること）— P1: じゃらん本番化

最小で価値を出し、かつ安全に在庫連動を本番化する範囲。**この順で実装**する。

| # | タスク | 出典 | 種別 |
|---|---|---|---|
| 1 | じゃらん `DATE_HEADER`/`NEXT_BUTTON` セレクタを本番DOMで最終確定 | 03 §7 | 確認 |
| 2 | **二重減算防止**: `dedup_key={source_site}:{bookingNo}` をpayload追加＋Actions側で処理済み照合、GAS側 `SLOT_SYNCED`列記録 | 01 §4.2 / 03 §4.4 | 実装 |
| 3 | **サイレント失敗の排除**: セレクタ不在/枠未検出を `exitCode=1` で異常終了化 | 03 §4.3 | 実装 |
| 4 | **失敗のLINE通知**: Actions `if: failure()` でLINE push（在庫.失敗 ALERT） | 02 §2.7 / 03 §4.4 | 実装 |
| 5 | 実行ログを成功時もartifact常時保存 | 03 §4.5 | 実装 |
| 6 | `GITHUB_TOKEN` を期限付き・最小権限（Fine-grained PAT）へ | 03 §4.1 / §5 | 運用 |
| 7 | DRY_RUNで1枠検証 → `DRY_RUN=false` で実減算1件 → 確認 → 本番ON | 03 §6 P1 | 検証 |

**P1完了条件**: `DRY_RUN=false`で実枠が正しく減る／失敗時にLINEが届く／同一予約の再dispatchで二重減算しない／セレクタ不在で必ず異常終了する。

その後: P2 セレクタ健全性監視 → P3 マルチOTA → P4 予約リコンサイル → P5 在庫リコンサイル（[03章 §6](./03-architecture-ops.md)）。

## 8. 主要な未決事項（意思決定が必要）

3編の未決事項から、**事業判断が要るもの**を抜粋。実装前にオーナー確認。

1. **仮予約段階で在庫を減らすか**: 推奨は「確定時のみ減算」（過剰減算防止）。現状コードは仮予約でも減算を呼ぶ。→ 01 §7
2. **在庫連動の本番ON時期**: ON前提でないと「在庫失敗ALERT」の価値が出ない。→ 02 §7
3. **dispatch成功≠実在庫減算**の検証手段: コールバック / 逆dispatch / 手動確認のどれか。→ 02 §7 / 03 §7
4. **取りこぼし(MISSING)検出時、在庫減算まで自動化するか**: 二重減算リスクとのトレードオフ。→ 03 §7
5. **マルチOTA自動操作の規約・リスク**: 各OTAのロボット操作可否、アカウントロックの事業リスク。→ 03 §7
6. **他3OTA（アソビュー/AJ/ウラカタ）の管理画面**: ログイン方式（2FA有無）・セレクタの現物確認が必要（じゃらん同様の録画）。→ 03 §7
7. **通知ログ・日次サマリーのデータ源**: 予約用SS / 分析用SS のどちらを正とするか。→ 02 §7

## 9. リスクと対策（要約）

| リスク | 影響 | 対策 | 出典 |
|---|---|---|---|
| 二重減算 | 売れる枠を過剰に閉じる | dedup_key（P1必須） | 03 §7 |
| サイレント失敗 | 在庫が減らず気づけない | 異常終了化＋健全性監視 | 03 §4.3 |
| 2FA/CAPTCHA導入 | 自動化が突然停止 | セッション再利用＋手動フォールバック | 03 §4.2 |
| OTA UI変更 | セレクタ破綻 | sites.json外部化＋カナリア監視 | 03 §3.2/§4.3 |
| アカウントロック | 販売停止＝事業停止 | レート制御・低頻度ログイン | 03 §4.6 |
| 通知ロスト | 障害見逃し | postToLine_リトライ＋通知ログ | 02 §3 |

## 10. まとめ

- 既存システムは**取込・カレンダー・通知・週次分析まで稼働**。在庫連動はじゃらんでPoC成功済み。
- 次の一手は **P1: じゃらん在庫連動の安全な本番化**（二重減算防止・失敗通知・サイレント失敗排除が必須ゲート）。
- その先に**マルチOTA**と**定期リコンサイル**を段階導入すれば、「どこで予約が入っても全チャネルの在庫が自動で揃う」状態に到達する。
- 詳細は各編（01/02/03）を参照。実装は本書 §6 のMVPタスク順で着手することを推奨。
